masedet remote test runner: plan

Run real tests on masedet's DevSandbox clones from a repo agent, with no login · draft 2026-11-25 · nothing built yet
Not too ambitious. It is a small project: two PowerShell scripts and one config file in the ops repo (masedet-ws-ops), one scheduled task on masedet, and one small command on the agent side. masedet keeps reaching out only (GitHub pull, SharePoint sync), so no firewall or access rule changes. The one design rule that makes it safe: a request names a job from a fixed list; it never carries a command.

Full implementation plan (for the agent that builds it): masedet-remote-testing-plan.md

How one test run travels

1 · input

Request

The agent pushes a small request file: which repo, which job.

agent sandbox → GitHub
2 · listener

Poll

A scheduled task pulls the requests every few minutes and picks up new ones.

masedet · Task Scheduler
3 · executor

Run

Looks the job up in the allowlist and runs it in that repo's DevSandbox clone, with a timeout.

masedet · PowerShell
4 · output

Result

Full log to the shared folder; a short summary back to GitHub.

SharePoint + GitHub
5 · listener

Wait

The agent waits for the summary, reads it and reports.

agent sandbox

Expected round trip: 5–10 minutes (one poll interval plus the job's own run time).

The five parts

Safety rules built in

What a request can do

  • Pick a repo and a job name. Nothing else. Unknown names are refused and logged.
  • The commands live in the ops repo's catalogue, which changes only by a PR you merge.
  • DevSandbox only: the executor refuses any folder outside D:\Scripts\DevSandbox\.
  • The job's environment has no production Alma key.

What can't go wrong quietly

  • Each request runs once. An id that already has a result is skipped.
  • Requests older than 2 hours are ignored, so a stuck backlog can't fire weeks later (the lesson from GH #48, the failed-folder change).
  • One job at a time, with a lock file and a hard timeout that kills the whole process tree.
  • Kill switch: disable the task, or drop a remote_jobs.disabled file.
  • Every request, accepted or refused, is written to a log on masedet.

What leaves TAU

  • The Alma sandbox is a copy of production, so logs can name real patrons. Full logs therefore stay in SharePoint.
  • GitHub gets only the summary. A job may add the last lines of its output (publish_tail) when that output is known to be clean, such as pytest.

IT

your call

No rule is changed, but this is a way to start jobs on a managed machine from outside it. Worth one sentence to IT before the task is registered: "a scheduled task that runs a fixed list of test commands, triggered by a file in our GitHub repo".

Phase 1 alone is already useful: you would trigger by pushing a file and read the log in SharePoint. Phases 2–3 are what remove you from the loop.

Decisions for you (phase 0)

  1. Where requests live. A new private repo masedet-jobs (recommended: keeps request noise out of the ops repo's history, and agents never need to push to the ops repo's main branch) or a jobs branch in masedet-ws-ops.
  2. How results come back to the agent. Summary pushed to GitHub (recommended; needs masedet's SSH key to have write access to that one repo), or SharePoint only, with a small copier in WSL that drops results into the agent's folder the way screenshots already arrive.
  3. IT. Tell them first, or treat it as one more scheduled task like the auto-deploy?
  4. Jobs that write to the Alma sandbox. Allowed in the catalogue (needed for the end-to-end check), or read-only jobs only at first?

What I don't know yet

  • Whether masedet's current GitHub SSH key can push, or only pull.
  • Whether the auto-deploy also updates the masedet-ws-ops clone on masedet, or you pull that one by hand. The executor must always run the merged catalogue.
  • Whether _ops_shared syncs to your PC as well as to SharePoint.

For the 0.7.0 bump, none of this is needed

The missing Sandbox check can be done today by dropping one lending and one borrowing test file into the synced DevSandbox input folders and looking at the Alma sandbox, provided those folders are the sandbox ones and not production's.
